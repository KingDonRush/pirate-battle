# Design and implementation review

> **Read contract:** project review criteria derived from the brief and researched failure cases. Use when reviewing interface or implementation quality; recover task/authorization through [the index](../.agents/index.md). These criteria do not award rubric points.

[Merriam-Webster](https://www.merriam-webster.com/dictionary/slop) uses the term for low-quality digital content produced through AI, usually in quantity. For this project, the following are our engineering and design applications of that definition, not a published universal scoring standard.

| Failure                                                      | Why it harms this game                                                                              | Replacement and review evidence                                                                                                                                                                                 |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Generic promises such as “an immersive, seamless experience” | They do not explain a control, status or decision.                                                  | Use specific text: “Time up”, “Score: 12”, “Match saved”, or “Match not saved. Try again”. Check each message in its actual state.                                                                              |
| A dashboard-like shell with decorative statistics            | It makes the next game action harder to locate.                                                     | Play is the primary menu action; options and data tabs are secondary. During combat, show health, score, remaining time, pause and controls. Review a phone screenshot at normal scale.                         |
| Invented visual style unrelated to the supplied pack         | It fragments the scene and adds asset work under a short deadline.                                  | Use the supplied naval sprites, water/sand tiles and wood/metal panels. Establish consistent spacing, type size and button states. Inspect complete screens together.                                           |
| Image-based buttons without semantics                        | A screenshot looks complete while keyboard and assistive interaction fail.                          | Build real buttons/labels/dialogs, using art as presentation. Verify Tab, Enter, Escape, focus return and accessible errors. See [W3C dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). |
| A generic engine framework or wrappers hiding simple logic   | Every rule requires tracing through extra files and concepts.                                       | Keep a direct simulation update and explicit systems. A helper must remove actual duplication or own a lifecycle. Follow the path from one input to one impact and count the decisions needed.                  |
| Applying a downloaded skill by keyword                       | React/Next.js/SWR recommendations can violate this challenge's browser-only and Query requirements. | Read the relevant rule, explain its purpose, and adapt it. Use React.lazy/Vite when useful; keep TanStack Query; skip server-component advice.                                                                  |
| Passing tests that set score or hit points directly          | The evaluator has no evidence that firing and collision work.                                       | Drive inputs, advance the real clock and observe immutable state/rendered effects. Test instrumentation cannot award points or force results.                                                                   |
| A screenshot baseline update used to hide failure            | It preserves the regression as the new expected image.                                              | Inspect the actual difference and approve a changed design before replacing a baseline. Keep baselines deterministic and versioned.                                                                             |
| Claims of “60 FPS” or “100% complete” without measurements   | They conceal the remaining assessment risk.                                                         | Record environment and p95 frame intervals; mark acceptance rows only after their associated checks pass.                                                                                                       |

Use healthy, damaged and destroyed ship variants to distinguish state. Keep explosions short, hit feedback readable, low health distinguishable beyond color, and reduced-motion behavior usable. Start with the visual references in the supplied pack and review the player ship, enemy roles and island boundaries at mobile scale.
